# 从能运行到能持续改进

每次迭代都形成一条证据链：**用户痛点 → 可检验假设 → 样例与指标 → 实现 → 前后对比 → 发布与复查**。

例如，“不打算联系客户”被提成待办：先加入一个不应生成待办的合成样例，确认旧版本失败，再只修改提示词或校验中的一个因素。检查原始误提和最终误提都是否改善，同时检查其他样例是否退步。把坏例变成可复现资产，才能减少下次升级时重复犯错。

## 两条独立的验证线

| 验证 | 回答的问题 | 运行方式 | 不能证明什么 |
| --- | --- | --- | --- |
| 系统测试 | 保存、状态、队列、并发、恢复是否可靠 | `python -m unittest discover -s tests -v` | 模型是否理解了含义 |
| 离线合约回归 | 固定响应经过评分与应用校验后，是否出现已知退步 | `python -m evals.run --baseline evals/baselines/contract-v1.json` | 真实模型准确率、费用或速度 |
| 真实模型评测 | 当前模型 + 提示词在固定合成输入上的输出如何 | 显式 live 命令 | 个人全部日记的质量和泛化能力 |
| 人工复核 | 引用是否真正支持结论、措辞与任务状态是否忠实 | 审阅 JSON 输出和原始合成样例 | 不能替代系统可靠性检查 |

离线合约使用独立手写响应，标注与响应分开存储；它不调用模型。新加入的评测器测试会故意制造错误，确认错误会被检测。CI 无模型密钥、无付费调用，也不访问本机日记目录。

## 一次真实模型实验

在项目目录打开 PowerShell。先在当前终端设置 `DIARY_EVAL_API_KEY` 环境变量；不要写入仓库、脚本或聊天。地址使用提供方控制台当前的 OpenAI 兼容 Base URL，模型使用实际模型 ID。

```powershell
# 先用 1 个合成样例检查兼容性；命令不会读取应用配置或个人日记
python -m evals.run --mode live --allow-cloud --base-url "https://YOUR-HOST/compatible-mode/v1" --model "YOUR-MODEL-ID" --case e01

# 通过后跑完整的 24 个公开合成样例；每例最多调用一次，不自动重试
python -m evals.run --mode live --allow-cloud --base-url "https://YOUR-HOST/compatible-mode/v1" --model "YOUR-MODEL-ID"
```

本地模型可省略 `--allow-cloud`，地址必须指向本机回环地址。云端命令只有显式允许并设置密钥环境变量才会运行；不会读取应用的密钥文件。每次全量实验是 24 次串行请求，单次超时 75 秒；建议先跑单例再自行决定是否承担全量调用费用。

报告默认在被 Git 忽略的 `.eval-results/`，同名 JSON 供比较，Markdown 供阅读；每次生成独立文件，不覆盖旧报告。需要保存基线时，先人工审核报告，再将选定 JSON **复制**到自己的基线目录。不要把未经审阅的报告直接加入公开仓库。

```powershell
# 替换为两次实际生成的完整报告路径
python -m evals.compare .eval-results/BASELINE.json .eval-results/CANDIDATE.json

# 也可以在运行候选实验时直接指定此前真实实验的基线
python -m evals.run --mode live --allow-cloud --base-url "https://YOUR-HOST/compatible-mode/v1" --model "YOUR-MODEL-ID" --baseline .eval-results/BASELINE.json
```

比较器拒绝混用离线与真实结果，或混用数据集、评分器、门禁版本及样例子集。提示词和模型允许改变，因为它们正是实验变量；每次尽量只改变一个因素。离线替身改变后也必须人工审阅并建立新的合约基线，不通过随意刷新基线来消除失败。

费用字段默认空值。可以显式传 `--input-price` 和 `--output-price`，单位为人民币 / 百万 tokens；仅当每例都有有效用量时提供估算。该估算不处理缓存折扣、阶梯单价、提供方额外计费或失败请求费用，应以实际账单为准。`enable_thinking` 和 `response_format` 目前未发送，由提供方默认行为决定；报告中空值表示未设置。

## 评分口径与局限

- 行动使用类别、原文锚点、标题表达式进行一对一匹配；重复算误提，未匹配标注算漏提。它允许有限改写，但仍可能误判语义相同的表达，需人工核对。
- 原始输出和应用校验后分别计算精确率、召回率、F1。无分母的指标显示空值，不用 100% 填充。
- 错误生成的 task 算严重误提；多余或错误关联的完成事件算误关闭。只引用了正确原文，也可能关闭了错误的已有行动，因此单独测完成 ID 与关联 ID。
- 日期正确率只在匹配行动上计算，漏行动另由召回率惩罚；模糊日期的标注值为 null。引用有效率仅检查逐字存在，不能证明推论正确。
- 每日回顾测结构、来源引用与预期记录覆盖。它**尚不自动测量摘要事实忠实度、状态措辞、信息密度或可读性**；这些必须逐例审阅。
- 请求或解析失败保留为失败样例，预期行动仍算漏提；不把失败样例移出分母。
- 真实延迟包含请求与解析，p50/p95 是本次有限样例的观测值，不是服务 SLA。用量缺失显示缺失，不当作零。

当前门禁：结构与引用全通过；原始和最终误提待办 / 误关闭均为零；F1、日期、关联、完成召回、每日来源覆盖至少 0.9；与相同输入的已审核基线相比不得出现观测退步。24 个样例较少，不能据此宣传高准确率。

真实模型的随机性可能导致波动：至少重复 3 次并保留每份报告，失败时分析具体样例。当前工具不做显著性检验，也不自动选出“最优模型”。

人工复核至少记录：摘要是否忠实；引用是否充分；承诺与建议是否分清；完成的是否是正确任务；遗漏了什么；是否凭空补充日期或事实。采用“通过 / 待修正 / 拒绝”，说明证据，不用模型自评分充当质量结论。

## 版本与发布流程

1. 用问题模板记录痛点、合成复现、预期行为与指标。先确定验收条件，再改代码。
2. 修改提示词时提升 `app/prompts.py` 中对应版本，再运行 `python -m evals.register_prompts`；旧版本哈希不能被覆写。登记文件和提示词一同审阅。
3. 新增 / 修改标注时提升数据集版本；修改评分含义或门禁时分别提升评分器 / 门禁版本。同一小组实验冻结这些变量，否则新建基线。
4. 跑系统测试、离线合约回归、内容检查；AI 行为变更还需要真实模型评测与人工复核。全绿 CI 只允许说明自动检查通过，不能替代尚未进行的真实实验。
5. 更新 `CHANGELOG.md`、路线图和验证依据。使用应用版本号；修改数据结构前必须补迁移测试与升级前备份，不能让升级损坏旧数据。
6. 将经过审阅的提交发布到 GitHub。保留旧提交与报告；回退代码前先看数据兼容说明，不通过复制旧数据库覆盖新数据。

每份报告记录应用版本、Git 提交及工作区是否有未提交修改、提示词版本与 SHA、数据集版本与 SHA、评分器和门禁版本、样例集合、模型和请求选项。模型别名可能变化，能获取时同时记录提供方返回的模型名。后续版本应把这些信息也附到正式分析结果，当前正式数据库尚未保存提示词版本。

## 从使用反馈走向下一轮

v1.2 已为长期记忆增加认可、修正和删除入口；单条日记分析的误提 / 漏提反馈仍计划后续实现，目前使用 GitHub 问题模板手动登记合成复现。个人原文、修改次数和使用行为不会自动上传或遥测。待样例积累后，再划分开发集与隐藏回归集，减少只针对公开样例优化的风险。

可在本机手动观察记录成功率、整理等待时间、错误修正次数、接受的建议是否有帮助；在获得真实数据前，不写提升效率百分比。迭代节奏由这些问题和证据驱动，路线图不等于已经实现。
