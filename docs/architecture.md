# 数据与智能整理

## 运行结构

本机浏览器 → `127.0.0.1` 本地 HTTP 服务 → SQLite。AI 请求仅由本地服务按保存的选择发起。依赖 Python 3.10+ 标准库，无需前端构建或联网安装包。

正式数据默认放在项目的独立 `data/` 子目录，排除在源码版本管理之外，独立于浏览器缓存与构建产物。Windows 启动器和默认命令启动使用同一位置；命令启动也支持 `SHIGUANG_DATA_DIR` 或 `--data-dir` 指定独立目录。迁移先退出服务，保留密钥与外部备份，验证完整性后再处理旧目录。

桌面启动按数据目录使用命名互斥量串行执行，先读取 `runtime.json` 并核对应用标识与实际数据目录，只有同一份日记才复用服务。端口不可用时在绑定阶段改用系统分配端口，不先查空闲再启动；确认实际端口后原子写入运行信息并自动打开地址。不同项目与其他日记实例不会被停止。Windows 使用 `SO_EXCLUSIVEADDRUSE`，避免共享监听端口的不确定行为，依据见 [Microsoft 端口绑定说明](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse)。同源检查始终使用实际监听端口。

## 关系

| 表 | 用途与约束 |
| --- | --- |
| entries | 原文、创建/更新时间、所属日、时区、版本、AI 纳入开关 |
| entry_versions | 每次文字保存的历史，记录 ID + 版本唯一 |
| attachments | 原件元数据，内容哈希定位本机文件，独立的不透明访问编号 |
| media_versions / entry_media | 附件排布历史，关联对应文字版本；Unicode 码点位置与排序 |
| analyses | 当前版本的结构化分析，过期版本不可写回 |
| actions | 独立行动状态、类型、期限、归一化指纹、用户修改标识 |
| action_sources | 行动与记录的多对多关联，保留版本及引用 |
| action_history | 操作前后快照，用于可校验的撤销 |
| daily_summaries | 每日回顾、上下文签名、模型与更新时间 |
| jobs | 持久化队列，同类型/目标唯一，任务票据随重新入队更新 |
| settings | 非密钥配置；密钥单独由 Windows DPAPI 保护 |

每次连接启用外键，使用参数化查询与事务。日记数据库版本为 4；v1–v3 升级前创建快照，拒绝更高版本。`growth_receipts` 保存分片结果与进度，`memory_exclusions` 保存自动积累的单条排除。备份使用 SQLite backup API、临时文件、完整性检查、原子替换。个人档案的关系与撤回机制见[档案设计](personal-archive.md)。

附件采用 SQLite 元数据 + 不可变原件文件，独立版本避免增删照片触发付费文字分析；备份镜像与便携 ZIP 负责保留原件，见[媒体与备份设计](media.md)。

可选的视觉命名在上传后单独运行：本机规则筛选无意义文件名，浏览器生成不含拍摄元数据的缩略图，`MediaNamer` 在独立开关和输入边界检查后调用统一 `ModelClient`。按原件、服务、模型和协议版本缓存，进程内锁合并同时到达的重复请求；网络期间不持有日记数据库锁。名称作为 `entry_media.label` 进入附件版本，而非覆盖 `attachments.name` 或重命名物理文件。原件不进入文字分析，实际视觉调用沿用独立费用账目。

## 分析流程

1. 原文事务提交后入队；单条分析先于每日整理。
2. 未配置 AI 的任务标记 waiting，不伪造结果。配置后自动重新入队。
3. 请求携带记录创建日期、时区和有限的已知行动上下文；仅纳入允许分析的记录。
4. 校验 JSON 版本、类型、枚举和原文引用。引用不存在、日期缺乏依据或无效关联会拒绝写回。
5. 写回前检查任务票据与当前记录版本；在途旧请求不会覆盖新输入。
6. 行动按已有 ID 或规范化标题指纹合并。用户修改与取消状态受到保护。模型明确识别完成时保留历史与来源，可在行动列表重新打开。
7. 每日输入包含当日允许分析的全部原文、现有分析和关联行动状态。上下文签名改变会使旧回顾标记待更新；提交时再次比对签名。
8. 超时、限流或格式错误有限重试三次；之后显示失败与重试入口。进程重启后恢复运行中任务。

生产后台将自动每日回顾延后到最后一条分析完成约 30 秒后，连续写入只保留同一日期的一个任务。手动重新整理可以立即运行。已提交的分析 JSON 与每日回顾 JSON 附有 `_cache` 回执，绑定来源内容、服务 / 模型、提示词、上下文版本与结果哈希；自动重放先验证再复用，不重复写行动历史。显式重新整理会清除该项回执，允许用户获取新结果。

`request_context.py` 只处理发送格式：每日保留完整原文与最终行动状态 / 期限，省去重复的派生分析和引用；结构化 ID 使用请求内的临时短编号，返回时还原到原始来源。引用正文不替换，未知编号仍由原校验器拒绝。缓存命中不发起请求，独立费用账目只记真实模型调用。

`organization.py` 在模型调用之前选择简单原文回顾，在 API 读取时为已有结果做去重复呈现。两个阶段分开：前者能避免一次额外推理，后者只能减少阅读负担。简单回顾保持格式版本 1，派生 JSON 记录本机原文标记，正文从当前允许的来源按需读取；显式重新生成使用任务版本标记绕过自动选择。画像按独立来源与日期 / 阶段决定是否开始尝试，不把同一来源的多张卡当成多次经历。

单条提取模板 `ENTRY_PROMPT` 和每日整合模板 `DAY_PROMPT` 位于 `app/prompts.py`。JSON 输出契约以模板与 `app/ai.py` 中的 `validate_entry` / `validate_day` 为准。

## 请求记账

`app/usage.py` 使用独立的 `data/usage.sqlite3`（账目结构版本 1），保存用途、模型、时间、重试次数、服务返回的用量和当次单价。不保存提示词、原文、回复与密钥。独立账目避免“恢复旧日记”让已发生的消费消失；业务 JSON 备份不包含账目，账目有单独 CSV 导出及 `usage-日期.sqlite3` 每日快照，位于当前备份目录。

生产请求由 `ModelClient` 统一记账。发送前先落一条进行中记录，响应到达先提取 `usage`，再解析模型内容。进程重启把未完成记录标为中断与未知；单次记账失败不会触发新的付费请求。独立快照失败在费用页提示，不影响已保存的日记。

输入与输出费用采用十进制定点计算，价格快照绑定服务端点与请求模型；缓存命中和思考 Token 为子集，不重复相加。缺失字段保留为空，部分已知费用与未知次数分别展示。仅兼容 Chat Completions 用量字段，实际计费可能受阶梯单价、缓存、免费额度和折扣影响，页面不冒充服务商账单。

自动积累是独立的一次性设置：新记录复用单条请求，旧记录分片，缓存按来源版本、内容签名和提取提示词版本校验。画像使用最多 24 条有覆盖标记的记忆，月度回顾最多使用两个月各 10 份缓存原文片段；不反复发送完整历史。每日额外次数与已知估算预算在请求前检查，异常中断不自动付费重试。原有手动模式仍可使用，普通每日回顾仍发送当天允许分析的原文。

## 可靠性与限制

标题指纹是确定性去重，语义相同但用词不同的任务需依靠模型返回已有行动 ID。模型是概率系统，结构及原文引用校验不代表结论必然正确；界面保留原文依据和修改入口。取消采纳的行动保存为 dismissed，不物理删除，以免下次分析重新出现。

正式日记与浏览器缓存独立；草稿仍受浏览器环境影响，必须看到保存成功才视为正式入库。SQLite 数据库未额外加密，DPAPI 仅保护 API 密钥。本地服务并非公网托管服务器，不应改为向公网监听。

本地模式限制请求目标为回环地址且禁用重定向，但无法代替用户核实本地模型服务是否再次转发内容。没有 AI 外部凭证时，真实推理质量与第三方服务可用性留待配置后验证。
